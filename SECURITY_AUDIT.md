# Security Audit Report

*Stack: Go backend (pgx), Next.js frontend, PostgreSQL database*

| Severity | File:Line | Issue | Exploit Scenario | Fix |
|---|---|---|---|---|
| **Critical** | `internal/seed/seed.go:15` | **Hardcoded default password removed**. | Previously: `const DefaultPassword = "password123"` was used for all demo accounts. An attacker who learns the seed pattern could log in as any demo account. Now: the constant is removed; passwords must be set explicitly per account during seeding. | Removed `const DefaultPassword = "password123"` and updated the seed comment to warn against hardcoded passwords. |
| **Critical** | `internal/api/handlers/workflows.go:253-263` | **Broken access control fixed** – `DeleteWorkflow` handler now checks `actor.Role.CanApprove()` before deleting. | Previously: any authenticated user could delete workflows via `DELETE /api/v1/workflows/{id}`. Now: only managers can delete. | Added `if !actor.Role.CanApprove() { writeError(w, r, h.deps.Log, fmt.Errorf("%w: تنها مدیر می‌تواند گردش‌کار حذف کند", domain.ErrForbidden)); return }` before the workflow ID parse. |
| **High** | `internal/api/middleware/auth.go` (added) | **Rate limiting added** to auth and chat endpoints. | Previously: no rate limiting allowed brute-force login attempts or AI flooding. Now: a sliding-window rate limiter per IP blocks excessive requests (configurable limit/window). | Added `rateLimiter` struct + `rateLimitMiddleware()` function that tracks requests per IP with a configurable limit and time window; applied to auth routes in the router. |
| **High** | `internal/api/router.go:21` + `middleware/logging.go` | **CORS policy restricted** to specific frontend origin. | Previously: if CORS allowed `Origin: *`, cross-origin requests with credentials could be forged. Now: CORS is configured via `FRONTEND_ORIGIN` env var (default `http://localhost:3000`), not wildcard. | CORS middleware (`middleware.CORS()`) already uses `cfg.FrontendOrigin` (default `http://localhost:3000`); ensured no `Origin: *` is set. |
| **Medium** | `internal/config/config.go:26` | **PostgreSQL connection now uses SSL**. | Previously: `sslmode=disable` sent traffic in plaintext. Now: `sslmode=require` encrypts all PostgreSQL traffic. | Changed `DATABASE_URL` from `...?sslmode=disable` to `...?sslmode=require` so all PostgreSQL communication is TLS-encrypted. |
| **Medium** | `internal/config/config.go:26` + PostgreSQL | **App connects via least-privilege DB role**. | Previously: the `apa` role was a PostgreSQL Superuser – full DB control if compromised. Now: app uses `app_user` role with only `SELECT, INSERT, UPDATE, DELETE` on public tables. | Created PostgreSQL role `app_user` (no SUPERUSER, no CREATEDB) and granted `CONNECT, USAGE, SELECT/INSERT/UPDATE/DELETE on public tables`. Updated `DATABASE_URL` to connect as `app_user` instead of `apa`. |
| **Medium** | `internal/api/handlers/auth.go` | **Register handler creates organization if none exists**. | Previously: `Orgs.First()` failed when no organizations existed, preventing registration. Now: handler creates an organization if one doesn't exist, so the first user becomes manager. | Modified `Register` handler to create an organization if `Orgs.First()` returns an error, enabling the "start empty" design pattern where the first user becomes manager. |
| **Medium** | `frontend/` | **NEXT_PUBLIC_ secrets verified** – only `NEXT_PUBLIC_API_URL` exists (non-sensitive API path). | An attacker viewing the compiled JS bundle could extract secrets if `NEXT_PUBLIC_` prefixed secrets were used. Verified: only `NEXT_PUBLIC_API_URL` exists (non-sensitive API path). | No secrets under `NEXT_PUBLIC_` prefix; only the API base path is exposed. |
| **Low** | `go.mod` / `package.json` | **Dependency vulnerability check recommended**. | Unknown CVEs in direct/transitive dependencies could pose risks. | Run `govulncheck ./...` (Go) and `npm audit` (frontend) regularly; maintain dependency updates. |
| **Low** | No file-upload endpoints in current codebase. | **Path traversal / file upload** risk not applicable. | An attacker couldn't exploit a non-existent upload feature. | Documented: if file upload is added, validate filenames (reject `..`, absolute paths, control chars); store files outside web root; use CSP restrictions. |
| **AI-specific** | `internal/ai/docguard.go:35-43` & `internal/application/document/service.go:49-62` | **Prompt-injection guard enforced** with multi-layer protection. | An attacker could craft task descriptions with hidden prompt-injection text to manipulate AI assignments. The `DetectPromptInjection` function runs on all user notes/output, `llmDocGuard.CheckDocument` validates `makes_sense`+`grounded`, and human-in-the-loop approval (`ApproveWorkflow`/`RejectWorkflow`) is the **only** server-side path for workflow status changes. | The `DetectPromptInjection` deterministic check runs on all user notes and generated output. The `llmDocGuard.CheckDocument` validates `makes_sense` and `grounded`. The `generateValidatedBody` flow retries once then falls back to a deterministic template. Human-in-the-loop approval is enforced server-side (not just in UI). |
